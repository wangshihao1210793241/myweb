# Java 程序员用 Claude Code 写代码踩过的坑，我全帮你总结好了

作为一名 Java 后端开发，你一定经历过这种场景：产品提了个需求，你要在一坨祖传代码上做功能迭代，改完提测，发现原来的功能挂了。

最近我开始用 Claude Code 做 AI 辅助编程，踩了不少坑，也总结出了一套比较稳妥的工作方法。今天把经验分享出来，希望能帮到同样在做 Java 项目迭代的同学。

## 先说结论

Claude Code 和你平时用的 ChatGPT、通义千问不一样，它是一个**直接在你项目里改代码的 AI 助手**。你打开终端，告诉它要做什么，它就会读取你的项目文件、理解上下文、直接改代码。听起来很爽，但如果你不会"驾驭"它，很容易翻车。

下面从三个核心问题展开：**怎么提需求、怎么防改坏、怎么少出 Bug**，最后再给一套完整的工作流。

---

## 一、怎么提需求，AI 才能真正听懂

很多人用 AI 写代码，最大的问题不是 AI 不行，而是**需求没说清楚**。

### 1.1 一句话需求 = 灾难开始

你跟 AI 说"加一个用户导出功能"，它可能给你写了一个 CSV 导出，但你要的是 Excel。它可能没加分页，导出 10 万条数据直接 OOM。它可能没加权限校验，任何人都能导。

不是 AI 不聪明，是你没给它足够的信息。

### 1.2 结构化描述需求

好的需求描述应该是这样的：

> 在 UserController 里加一个导出接口 GET /api/users/export，支持按部门筛选（deptId 参数），返回 Excel 文件。用 EasyExcel 写。权限复用现有的 @RequiresPermissions("user:list")。

关键四要素：**在哪改、做什么、用什么技术、约束条件**。你给的信息越精确，AI 产出的代码越靠谱。

### 1.3 给上下文，不要假设 AI 全知道

如果你的需求涉及已有代码，直接告诉 AI 相关文件在哪：

> 先读一下 src/main/java/com/xxx/controller/UserController.java 和对应的 UserService，然后加一个导出接口

你也可以说"参考 OrderService 的写法"，AI 会自动去读那个类，保持代码风格统一。

### 1.4 需求拆小，分步交付

不要一次性说"重构整个用户模块"。拆成小块：

1. 先给 UserService 加个方法
2. 然后在 UserController 调用它
3. 最后补单元测试

每一步你确认没问题，再继续下一步。出了问题范围小，好定位，好回滚。

## 二、怎么防止 AI 改坏原有功能

这是大家最担心的问题。AI 改了代码，原来跑得好好的功能突然挂了，这种事情确实会发生。但有办法规避。

### 2.1 改动前让 AI 先分析影响范围

在需求后面加一句：

> 改之前先分析一下会影响哪些类和方法

AI 会先搜索引用关系，告诉你这次改动会波及哪些文件。你确认影响可控，再让它动手。

### 2.2 明确告诉 AI 哪些不能动

> 不要修改现有接口的签名，不要改数据库表结构，新增的代码不要影响已有逻辑

这种约束非常有效。AI 会严格遵守你的红线。

### 2.3 让 AI 写测试守住边界

> 给改动的方法补一下单元测试，重点是回归测试原有逻辑

测试是最好的安全网。尤其是 Service 层的业务逻辑，让 AI 写好测试，你部署前跑一遍，心里就有底了。

### 2.4 善用 git 随时审查改动

你随时可以问 AI："看一下改了什么"，它会执行 git diff 把变更列出来。如果你发现改了不该改的地方，一句话就能恢复：

```bash
git checkout .    # 一键恢复所有未提交的改动
```

## 三、怎么减少 AI 产出的 Bug

### 3.1 一定要指定技术栈版本

这步很多人会忽略，但真的非常关键。

> 项目用的是 Spring Boot 2.7 + MyBatis-Plus + JDK 8

为什么要指定版本？因为 JDK 8 没有 var 关键字，Spring Boot 2.x 和 3.x 的包名都不一样（javax vs jakarta），MyBatis 和 MyBatis-Plus 的 API 也不同。你不说清楚，AI 可能会用错版本的 API，代码编译都过不了。

### 3.2 明确边界情况的处理方式

> 注意处理空值、分页边界、并发场景

或者更具体：

> 如果查不到数据应该返回什么？如果参数校验失败抛什么异常？

把边界行为说清楚，至少能少一半的 Bug。

### 3.3 改完让 AI 自查一遍

> 改完后 review 一下自己的代码，看有没有遗漏

AI 会重新审视一遍自己写的代码，检查逻辑完整性和潜在问题。相当于双重检查。

## 四、分支管理：AI 到底在哪个分支写代码？

这是很多新手最困惑的问题。

答案是：**AI 就在你当前所在的分支上工作**。它不会主动切换分支，也不会自己创建分支。你在哪个分支打开 Claude Code，它就在哪个分支改代码。

### 推荐工作流

每次接到新需求，按照这个流程操作：

**第一步：拉功能分支**

```bash
git checkout dev
git pull
git checkout -b feature/user-export
```

**第二步：在这个分支上让 AI 开发**

```
你：在这个分支上加一个用户导出接口
AI：（在 feature/user-export 分支上写代码）
```

**第三步：审查并提交**

```
你：看一下改了什么
AI：（git diff 展示变更）

你：没问题，提交一下
AI：（commit 到 feature/user-export）
```

**第四步：推到远程，提 MR/PR**

```
你：推到远程
AI：（git push origin feature/user-export）
```

这样即使改坏了，最多丢一个功能分支，主分支永远不受影响。

### 几个关键原则

- **切分支、合并分支由你决定**，AI 只在你明确要求时才操作 git
- **AI 不会自动 push**，所有推送到远程的操作都会先征得你同意
- 如果你忘了切分支就开始干活，随时可以说"先 stash 一下，切到 feature/xxx 分支再继续"

## 五、一套万能需求模板

最后，给你一个可以直接复制粘贴的需求模板：

```
【目标】在 XxxController 加一个 Xxx 接口
【逻辑】接收 A 参数，调用 B 方法，返回 C 格式
【技术】用 D 框架/E 工具，参考 F 类的写法
【约束】不要改 G，注意处理 H 边界情况
【要求】改完后写单元测试，review 一遍
```

照这个模板写需求，你的 AI 协作效率至少翻一倍。
